## はじめに：月数百万トークンで青ざめた話

参画しているプロジェクトで、あるマイナーなAIエージェントツールを使い始めたところ、**月のトークン消費が数百万を超えてしまい**、コスト面で看過できない問題になりました。

### 背景：いま起きている「従量課金シフト」

ここ1〜2年、AI開発ツール業界全体で**定額制から従量課金（あるいはハイブリッド）への移行**が進んでいます。

- **GitHub Copilot**: 2025年から「**Premium Requests**」制を導入。Pro $10では月300回、Pro+ $39でも月1500回までで、それを超えると追加課金。GPT-4.1や Claude Sonnet等の重モデルは消費倍率が高く、エージェント実行は1回で複数リクエストを消費します
- **Cursor**: 2025年中旬に Pro プランの「500 fast requests」をやめて、**従量＋月額枠**のハイブリッドに変更。重いタスクを回すユーザーは追加課金へ
- **Anthropic Claude (Max)**: $100/$200の上位定額でも**週次の使用上限**が設定された
- **Windsurf / Cline / Roo Code 等**: API直叩き型ツールは元から従量、利用量に応じて青天井

「**月額固定で使い放題**」の時代から、「**使った分だけ課金される**」時代に明確にシフトしています。エージェント機能の普及により**1タスクあたりのトークン消費が数倍に膨らんだ**ことが背景にあり、各社とも持続可能なモデルとして従量化を選んだ形です。

AIエージェントは「便利な分だけ青天井で課金される」性質があり、無対策で本気運用すると、簡単に**個人の月数万円〜、チームなら数十万円〜**の請求が飛んできます。

> **問題意識**
> - 従量課金は使うほど高くなる（あたりまえだが体感が遅い）
> - エージェント系はツール呼び出し・思考・読み込みで**裏で勝手にトークンを消費**する
> - 「便利だから」で放置していると、四半期で予算をぶち抜く

そこで、Claude Codeを中心に、**AIツール全般のトークン・課金削減策**を、自分の整理を兼ねて体系的にまとめます。

特に以下のような方を対象にしています：

- Claude Code / Cursor / Copilot / Cline / Continue 等を日常的に使う個人開発者
- AIエージェントを本格運用しているが、コストに頭を悩ませているチーム
- 「とりあえず使えてはいるが、これって本当に最適？」と疑問を持っている方

## この記事のゴール

1. AIツールのコスト削減策を **8カテゴリ × 計15+項目** に整理する
2. よくある疑問（実際に自分が悩んだ点）をQ&A形式で補足する
3. ユースケース別に最適解をステップで示す
   - **個人利用**：自由にツール・モデル選択ができるケース
   - **エンタープライズ**：モデルもツールも縛られているケース

## 全体マップ：削減策の分類

具体策に入る前に、削減策を以下の8カテゴリに整理しました。「何を削るか」の視点で大きく分かれます。

| カテゴリ | 何を削るか | 効果の桁感 |
|---|---|---|
| 1. キャッシュ活用 | 同一プロンプトの再課金 | 〜90% |
| 2. モデル選択 | 高単価モデルへの依存 | 〜80% |
| 3. コンテキスト最適化 | 不要な入力トークン | 30〜60% |
| 4. 出力制御 | 冗長な出力トークン | 30〜50% |
| 5. プロバイダ・契約形態の変更 | 単価そのもの | **70〜95%** |
| 6. ローカル/ハイブリッド構成 | API呼び出し自体 | 実質0（投資回収後） |
| 7. ワークフロー設計 | AIを呼ぶ回数 | 40〜70% |
| 8. 外部ツール連携 | AIに頼っていた処理 | 30〜50% |

「**頑張ってトークンを減らす**」より「**そもそも単価を下げる**」「**そもそも呼ばない**」方が桁違いに効きます。これは後で重要になります。

## カテゴリ1：キャッシュ活用

### 1-1. プロンプトキャッシング（Prompt Caching）

主要なAI APIには、**同じプロンプトの先頭部分（プレフィックス）を再利用すれば大幅割引**する仕組みがあります。

| プロバイダ | 割引率 | TTL | 指定方法 |
|---|---|---|---|
| Anthropic | 90% | 5分 / 1時間 | 明示（`cache_control`） |
| OpenAI | 50% | 5〜10分 | 自動 |
| Gemini (implicit) | 75% | 数分 | 自動 |
| Gemini (explicit) | 75% | 任意（保管料あり） | 明示 |
| AWS Bedrock | 〜90% | 5分 | 明示（`cachePoint`） |
| DeepSeek | 〜90% | 数時間〜長め | 自動 |
| Azure OpenAI | 50% | 5〜10分 | 自動 |

#### TTL（保持時間）の話

各社の表に「TTL」がありますが、これは **キャッシュがサーバ側で保持される時間** のことです。Anthropic/Bedrockは5分、OpenAIは5〜10分、Geminiも数分程度。**この時間を超えて再リクエストすると、キャッシュは失われ、再び「書き込み（フル課金 or 割増）」からやり直し**になります。

#### Q&A：キャッシュって、どこに保持されているの？

**A.** **プロバイダのサーバ側**でモデル内部のKVキャッシュとして保持されます。プロンプトのハッシュで照合される仕組みで、HTTP的にはステートレス。**別マシンから同じ内容を送ってもアカウント単位でヒット**します。Claude Codeは自動でキャッシュ指定を付けてくれるので、ユーザー側で特別な設定は不要。

#### 結局、人ができることは少ない

身も蓋もない話ですが、**プロンプトキャッシングについてユーザーができる工夫は「間を空けずに作業する」ことくらい**です。

- TTLは固定（変更不可）
- キャッシュ指定もツール側が自動でやっている
- プロンプト構造の最適化も、エージェント系ツールでは内部で決まっていてユーザーが触れる範囲は限定的

「重要な仕組みだが、能動的にできることは少ない」というのが現実です。**作業を細切れにせず、5分以内に連続実行する**——これを意識する程度で十分。逆に言えば、知らずに長時間放置してから再開すると、毎回フル課金が走るので**長時間離席するなら20分以上まとめる**方が結果的に得、という判断材料にはなります。

## カテゴリ2：モデル選択

### 2-1. タスクに応じたモデル使い分け

同じプロバイダ内でも、モデルにより単価は**5〜10倍**変わります。

| タスク | 推奨モデル例（Anthropic） |
|---|---|
| 単純な置換・フォーマット・要約 | Haiku 4.5 |
| 通常の実装作業 | Sonnet 4.6 |
| 複雑な設計・難デバッグのみ | Opus 4.7 |

Claude Codeは `/model` で切替可能。サブエージェントは frontmatter の `model:` で個別指定もできます。**惰性でOpusを使い続けない**ことが第一歩。

## カテゴリ3：コンテキスト最適化

### 3-1. サブエージェントによるコンテキスト隔離

大量のファイル探索やgrep結果は、メイン会話履歴を膨張させます。`Explore`等のサブエージェントに投げると、**最終要約だけが親に返る**ためメイン側のトークン消費が激減します。エージェントの内部処理で消費したトークンは、親会話の以降のターンには乗らないのがポイント。

### 3-2. `/clear` と `/compact` の積極活用

- `/clear`: 話題が変わったら即実行。前タスクの履歴を全消去
- `/compact`: 会話を要約圧縮。自動圧縮の前に手動で実行する方が制御しやすい

### 3-3. CLAUDE.md / memory / skillsで「毎回説明」を排除

プロジェクト規約・コーディングスタイル・よく使うコマンドを `CLAUDE.md` に書いておけば、毎セッション説明する必要がなくなります。
＊この辺りはよく見聞きするかと思います

`skills` は **再利用可能なワークフロー定義**で、`~/.claude/skills/` または `<project>/.claude/skills/` 配下にMarkdownで配置します（このスキル自体も `/create-article` という skill として実装されています）。「決まった手順を実行する」「特定の判断ルールを呼び出す」用途で、毎回手で説明していた内容を1回書けば永続化できます。slash commandから呼び出され、必要時のみロードされる**遅延ロード型**なので、大量に作っても基礎コストは低い設計です。

#### Claude Codeの memory の仕組み（補足）

`CLAUDE.md` と並んでよく使われる「memory」機能ですが、**実体はローカルディスク上のMarkdownファイル群**です。魔法的な仕組みはありません。

```
~/.claude/projects/<project>/memory/
├── MEMORY.md         ← 目次（毎ターン自動ロード）
├── user_role.md      ← 個別メモ（必要時に Read）
├── feedback_xxx.md
└── ...
```

- 起動時に**目次（MEMORY.md）だけ自動ロード**される（軽量）
- 個別ファイルは関連しそうなときだけClaudeが読み込み（遅延ロード）
- ユーザー嗜好・矯正履歴・プロジェクト事情・外部リソース等を**Claudeが自律的に書き込む**
- `CLAUDE.md`が「プロジェクトの憲法」なら、memoryは「Claudeが取った個人メモ」

トークン的には目次のみが固定コストで、**プレフィックスキャッシュが効きやすい**設計です。

### 3-4. ツール定義の削減（deferred tools / ToolSearch）

MCPサーバを大量に有効化していると、**全ツールのJSONSchemaが毎リクエストに乗ります**（数千〜数万トークン）。

- 使わないMCPサーバは `.mcp.json` から外す
- deferred tools方式で必要時のみ読み込む
- これだけで毎ターンの固定コストが激減

### 3-5. Read範囲の限定

- `Read` の `offset`/`limit` で必要な部分だけ読む
- 巨大ファイルをまるごとcatせず grep で該当行だけ取得
- ディレクトリ一覧は `find -maxdepth 2` で深さ制限、`node_modules`/`dist`/`.git` を除外

### 3-6. ツール出力の事前圧縮（RTK 等）

意外と見落とされがちですが、**Bashコマンドやテスト実行の出力**もコンテキストに丸ごと積まれます。`cargo test` や `npm test` のような数百テストの結果、`docker build` のログ、CIのフル出力——これらは1回で**数千〜数万トークン**を消費します。

これに対するアプローチとして、最近 [RTK（Rust Token Killer）](https://qiita.com/tanaka_taro_JP_KYUSYU/items/0565cc59862691982770) という Claude Code 用のCLIツールが登場しています。

#### RTK の仕組み

通常のLLM APIプロキシ（LiteLLM等、クライアント↔Anthropic間に挟むもの）とは**別レイヤー**で動きます。

```
従来:  Claude Code → Bashツール → コマンド実行 → [大量の出力] → Claudeコンテキストへ
RTK:   Claude Code → Bashツール → コマンド実行 → [大量の出力] → RTK圧縮 → [圧縮後] → Claudeコンテキストへ
```

Claude Code の **`PreToolUse` フック** を使い、Bashコマンドの出力を捕まえて要約・圧縮してからコンテキストに入れる仕組み。ユーザーには元出力が見え、Claudeに渡るのは圧縮版だけ。

#### 実測値（公式記事より）

- `cargo test`（262テスト成功）: **4,823 → 11 トークン（99.8%減）**
- 30分セッション全体: **150K → 45K トークン（70%減）**

インパクトは相当大きい。

#### 他の最適化との併用

- ✅ **プロンプトキャッシュとは別レイヤー**で動くので競合しない
- ✅ **LiteLLM / claude-code-router と併用可能**（APIプロキシとフックは独立）
- ⚠️ 圧縮しすぎるとClaudeがエラー内容を見落とす可能性。複雑なデバッグ時は対象コマンドを絞るなど調整が必要

「Hooksを活用したコスト削減」というカテゴリ自体がまだ新しく、RTKはその走りと言える存在です。Rust製の単一バイナリで依存なし、`rtk init -g --auto-patch` で `settings.json` 自動更新まで面倒を見てくれます。

## カテゴリ4：出力制御

出力トークンは入力より**3〜5倍高い**（Opusで入力$15 → 出力$75/MTok）ため、削減効果が大きい。

- 「200語以内で」「結論だけ」と明示
- 不要な要約・前置きを禁止（`CLAUDE.md`に記載）
- コード全体ではなく**Editツールで差分のみ**返させる
- API直接利用なら `max_tokens` で上限制御
- Extended thinking は難問のみON、雑談ではOFF

## カテゴリ5：プロバイダ・契約形態の変更

ここが**最も効果の桁が大きい**領域です。

### 5-1. 定額プランへの移行

トークン最適化を頑張るより、**上限のある定額に変える**のが最強の節約です。

- **Claude Pro / Max ($20〜$200/月)**: Claude Code込みで使い放題枠あり
- **Cursor Pro ($20/月)**: 500 fast requests＋無制限slow
- **GitHub Copilot ($10〜$39/月)**: 補完用途は圧倒的に安い
- **ChatGPT Plus ($20/月)**: Codex CLIも同梱

API従量で月$200超えているなら、**ほぼ確実に定額の方が安い**です。

### 5-2. 安価なAPIプロバイダへの切替

そもそも**単価が桁違いに安いプロバイダ**を使えば、最適化の努力よりはるかに大きな削減になります。

| プロバイダ | 特徴 |
|---|---|
| DeepSeek V3 / R1 | Claude Opusの**1/50〜1/100**の単価。コード性能はSonnet級 |
| Qwen3-Coder, GLM-4.6 | オープンモデルでも実用レベル |
| Kimi K2 (Moonshot) | 200万トークン文脈で激安、長文処理に強い |
| OpenRouter | 1キーで数十モデル使い分け |
| Cerebras / Groq | 推論速度が10倍速い |

### 5-3. Claude Codeで「Claude以外のモデル」を使う

ここで疑問になるのが、**「Claude Codeに慣れているのに、別プロバイダに乗り換える＝ツール自体を変える必要があるの？」**という点です。

結論：**Claude Codeはそのまま使ったまま、裏のモデルだけを差し替えることができます**。

Claude Codeは内部で **Anthropic互換のAPI** を叩いているだけなので、エンドポイントURLとAPIキーを環境変数で差し替えれば他モデルにルーティング可能です。これを**カスタムプロバイダ機能**と呼びます。

```bash
export ANTHROPIC_BASE_URL="https://your-proxy.example.com"
export ANTHROPIC_API_KEY="your-key"
```

公式に正規対応しているのは **Anthropic直 / AWS Bedrock / Google Vertex AI**（いずれもClaudeモデルが裏で動く）です。これに加えて、**Anthropic互換プロキシ**を挟むことで、DeepSeek/OpenAI/Gemini/ローカルLLMなど**実質どんなモデルでも繋げられます**。

#### 代表的なプロキシ

**LiteLLM Proxy**（汎用）と **claude-code-router**（Claude Code特化）が二大勢力です。どちらも目的は同じ「Anthropic形式の入出力を、別のプロバイダ形式に変換する中継サーバ」で、**設定方式と最適化対象が違うだけ**。

| ツール | 性格 | 特徴 |
|---|---|---|
| **LiteLLM** | 汎用統合（YAML設定） | 100+プロバイダ対応、コスト追跡・レート制限・キャッシュ等の運用機能も豊富 |
| **claude-code-router** | Claude Code特化（JSON設定） | タスク種別（background/think/longContext等）で自動振り分けが組み込み |

両者とも、**ブリッジ自作などの面倒な互換性対応は不要**で、設定ファイル数十行で動きます。

LiteLLMの設定例：

```yaml
model_list:
  - model_name: claude-sonnet-4-5
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_API_KEY
```

claude-code-routerの設定例（タスク別自動振り分け）：

```json
{
  "Router": {
    "default": "anthropic,claude-sonnet-4-6",
    "background": "deepseek,deepseek-chat",
    "think": "anthropic,claude-opus-4-7",
    "longContext": "gemini,gemini-2.5-pro"
  }
}
```

「日常作業は Claude、要約や長文読み込みは DeepSeek、長文だけ Gemini」と、**1セッション内で工程別に自動切替**できるのが claude-code-router の強み。「**メインは Claude のまま、安く済ませられるところだけ他社に逃がす**」というハイブリッド構成の現実解です。

#### プロキシ経由でも残る制約

形式変換は自動で吸収されますが、以下は変わりません：

- ⚠️ **モデルの賢さはそのまま**（DeepSeekはClaudeほどツール使用が上手くない）
- ⚠️ **Anthropic公式のプロンプトキャッシュ恩恵は消える**（代わりに他社側のキャッシュは効く）
- ⚠️ **Claude Code向けに最適化されたシステムプロンプト**と他モデルの相性問題

ただし「軽い処理だけ他社」というハイブリッドなら、これらの影響は最小化できます。

## カテゴリ6：ローカル/ハイブリッド構成

### 6-1. ローカルLLM

長期的に最強。**APIランニングコストが実質ゼロ**になります。

- **Mac Studio M3 Ultra**: Llama 3.3 70B, Qwen3-Coder 32B, DeepSeek-Coder V2が快適
- **RTX 4090/5090搭載PC**: 32B級がリアルタイム速度
- 推論サーバ: vLLM / llama.cpp / Ollama / LM Studio
- 接続: Continue.dev / Cline / Aider / Claude Code（LiteLLM経由）

特に効くケース：
- 機密コードでクラウドに送れない
- 1日100万トークン以上使う
- 補完・リファクタなど定型作業の比率が高い

### 6-2. RAG / セマンティック検索による事前圧縮

巨大コードベースをAIに探させると、grep結果・読込ファイルだけで数万トークン消費します。

- **Aiderのリポジトリマップ**: コードベース構造を圧縮表現で注入
- **Cursorの@codebase / Continueのembedding検索**: ベクトル検索で関連箇所だけ抽出
- **Sourcegraph Cody / Augment Code**: 大規模リポ向けのインデックス型補助
- **ast-grep / comby**: 構造的検索でAIを呼ばずに済ます

「AIに探させる」より「**渡す前に絞る**」方が圧倒的に安い。

## カテゴリ7：ワークフロー設計

**最強の節約は「呼ばない」**こと。AIに頼まずコードで自動実行できる範囲を広げるのが本質です。

- テスト/型/lintを先に整備 → 「ビルド通るか確認して」を10回頼まずに済む
- CI/pre-commitで自動修正 → prettier, eslint --fix, ruff format で定型直しはAI不要に
- **Claude Codeの hooks 機能**を活用 → イベントトリガで決まった処理を**コードとして実行**（AI呼び出しなし）。例：`PostToolUse` で編集後に自動フォーマット、`PreToolUse` で危険なコマンドをブロック、`Stop` で結果を通知。AIに「フォーマットして」「lintして」と毎回頼む必要がなくなる
- 明確な仕様書を最初に作る → 「どうする？」の往復が消える
- テンプレ・スキャフォルダー → 新規ファイル生成はcookiecutter/plopで
- 過去差分の使い回し → 似た作業のPRを人間が下書き → AIはレビュー/微調整だけ
- **バッチ思考**: 5個の小タスクを5回相談 → 1回にまとめる（システムプロンプト再送が4回分浮く）

ポイントは「**判断が必要な部分だけAI、決まりきった処理はコード**」と境界を引くこと。hooks やlinter、CIは“AIを呼ばないトリガ”として捉えると、設計時の選択肢が広がります。

## カテゴリ8：外部ツール連携

定型処理は専用ツールに寄せる：

- **コード補完**: GitHub Copilot / Cursor Tab（定額が圧倒的に安い）
- **検索**: ripgrep / ast-grep で事前絞り込み
- **リネーム**: sed / ast-grep（AI不要）
- **構造変換**: comby / jscodeshift

## ユースケース別の最適解

ここからが本題。**ピックアップして整理**します。

### ケース1：個人利用（自由度が高い）

**前提**：Claude Code等を普段使い、定額プランを利用中だがコストを下げたい、性能は落としたくない、慣れた体験を維持したい

#### 推奨：**「定額プラン継続 × claude-code-routerで一部処理を外部に逃がす」ハイブリッド**

| Step | アクション | 期待効果 |
|---|---|---|
| 1 | **使用量の現状把握**（`/usage` や ccusage 等）。Maxプランの何割を使っているか確認 | 判断材料 |
| 2 | `CLAUDE.md` と memory を整備し、毎回の説明を排除 | 10〜20%減 |
| 3 | 使わない MCP サーバを `.mcp.json` から削除 | 数千〜万トークン/ターン削減 |
| 4 | **RTK（Rust Token Killer）導入**でツール出力を自動圧縮 | セッション全体で**60〜90%減**の実測 |
| 5 | claude-code-router を導入し、**background（要約等）と longContext を DeepSeek に振り分け** | 定額枠が**1.5倍**持つ |
| 6 | コード補完を Copilot ($10/月) や Cursor Tab に分離 | Claude呼び出し回数が大幅減 |
| 7 | 1〜2ヶ月運用後、使用量データを見て**Maxプラン → Proへのダウングレード**を検討 | 月$80節約 |

**追加API課金**は月$5〜$15程度で収まることが多い。**性能を落とさず体験を維持**したまま、トータル**30〜60%減**が現実的。

#### やってはいけない罠

- ❌ メインコーディングまでDeepSeekに振る → ツール呼び出し精度が落ちて結局やり直し
- ❌ ローカルLLM中心への切替 → Mac Studio級がないと性能ガタ落ち
- ❌ Claude Codeをやめて他ツール → 慣れの損失が節約額を上回る

### ケース2：エンタープライズ（モデルもツールも縛られている）

**前提**：使用ツール・APIプロバイダ・モデルが社内ポリシーで固定、勝手な切替不可、ただしコストは下げたい

この場合、**カテゴリ5（プロバイダ変更）とカテゴリ6（ローカル）は使えない**ため、残りで戦います。

#### 推奨：**「設定×運用×ワークフロー」の三方向で削る**

| Step | アクション | カテゴリ | 期待効果 |
|---|---|---|---|
| 1 | **使用量の可視化**を最優先（ユーザー別・タスク別・モデル別）。ダッシュボードを作る | - | 判断材料 |
| 2 | チーム共通 `CLAUDE.md` / プロジェクト規約 / skills を整備し、不要な説明と手順の再説明を排除 | 3 | 10〜20%減 |
| 3 | MCPサーバ・ツール定義の棚卸し。**使っていないものを全削除** | 3 | 5〜15%減 |
| 4 | モデル使い分けルールを策定。**Opus相当の重モデルは設計レビューのみ**等、ガイドライン化 | 2 | 30〜50%減 |
| 5 | サブエージェント活用ルール（探索・要約は別エージェントへ）を周知 | 3 | コンテキスト膨張防止 |
| 6 | 出力制御の標準プロンプト整備（「結論のみ」「差分のみ」） | 4 | 20〜30%減 |
| 7 | hooks / CI / pre-commit で定型処理を自動化、**AI呼び出し自体を減らす** | 7,8 | 大きい |
| 7-2 | **ツール出力圧縮（RTK等）**をhooks経由で導入。モデル/APIを変えないので社内ポリシー下でも実現可能 | 3 | セッション全体で**60〜90%減**の可能性 |
| 8 | 月次レビュー：誰がどこで使ってるかを定期チェックし、ベストプラクティスをチーム共有 | - | 継続改善 |

**ベンダ・モデル変更ができないぶん、運用と設計の徹底で30〜50%減**が現実的なライン。

#### エンタープライズで特に重要なこと

1. **個人の頑張りに依存しない仕組み化**：規約・自動化・教育の3本柱
2. **可視化なくして削減なし**：まず「誰がどこで使っているか」を把握
3. **トップダウンの方針**：「設計だけOpus」「探索はサブエージェント必須」などのルールが現場任せだと守られない
4. **AIに頼らない部分を明確化**：定型処理はリンタ・テンプレ・スクリプトに寄せる文化を作る

## まとめ：効果の桁を意識する

| アプローチ | 削減効果の桁感 | 個人 | エンタープライズ |
|---|---|---|---|
| 小手先のトークン最適化 | 20〜50% | ◎ | ◎ |
| **プロバイダ・契約変更** | **70〜95%** | ◎ | △（制約次第） |
| **ローカル化** | 投資回収後ほぼゼロ | ◯ | △ |
| ワークフロー改善 | 40〜70% | ◎ | ◎ |
| 外部ツール分離 | 30〜50% | ◎ | ◯ |

**個人利用なら「プロバイダ・契約形態を見直すのが最も効く」**、**エンタープライズなら「運用と設計の徹底でじわじわ削る」**——これが結論です。

「便利だから使い続ける」のはOK。ただし、**便利の対価を払いすぎているかは定期的に見直す**価値があります。本記事が、その見直しのきっかけになれば嬉しいです。
